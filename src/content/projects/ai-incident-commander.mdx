**TL;DR**

- I designed and ran a **pre-registered, equal-budget comparison** of agent architectures for
  automated incident root-cause analysis — a single agent, a multi-agent commander, a Bayesian
  causal investigation engine, and [HolmesGPT](https://github.com/robusta-dev/holmesgpt) (the
  most widely deployed open-source SRE agent, a CNCF project) — across two domains, eight frozen
  experiments, and roughly 1,280 held-out runs.
- On 45 real microservice incidents, the **single agent matched the multi-agent system** at 1/3 the
  cost. A vote-of-three beat both. Four follow-up experiments showed the multi-agent advantage was
  **robustness, not reasoning**.
- **HolmesGPT, run unmodified, beat my single agent by 8.9 points** and matched the multi-agent
  system at **42% of its cost**. When I transplanted my agent's domain advice into HolmesGPT,
  it reproduced the same systematic errors — the same wrong answers in a completely different
  runtime.
- On 60 simulated AI-infrastructure incidents, the **single agent led overall (0.894)**, but the
  **causal engine found what others could not**: on retry-storm faults, it scored 0.72 where the
  single agent scored 0.06 — a 12× improvement on the hardest stratum.
- The causal engine's confidence signal actually works: at belief ≥ 0.80, **88.5% accuracy** vs
  66.4% below, while the single agent's self-reported "confident" was useless across 45 cases.
- **The whole programme cost $51 in model calls.** Every experiment pre-registered, every protocol
  frozen, every result reproducible from cassettes.

## Phase 1: the fair test nobody asked for

Multi-agent architectures are the default answer in agent design: add specialists, a coordinator, a
critic, and the system should reason better than one model alone. Most published comparisons let the
team of agents spend more, see more, or get tuned more than the single agent it is compared with.

I wanted a fair answer, so I built both systems and tested them the way you would test a clinical
trial: the same inputs, the same budget ceiling, an analysis plan written before the results, a
frozen protocol, and a held-out set nobody had looked at.

<IncidentArchitecture />

**The task.** When a microservice application degrades, the alert fires on a symptom (a slow
checkout page) while the cause is often several calls away. The benchmark is RCAEval RE2: two
open-source applications (Online Boutique, Train Ticket) with six kinds of injected faults. Given
the telemetry (metrics, logs, traces) and the alert time, rank the services most likely to be the
root cause. The metric is AC@1: how often the true cause is ranked first.

**The two systems**, built on the same model, the same seven read-only telemetry tools, the same
deterministic anomaly digest and the same per-incident ceiling:

- **Single agent (B1):** one tool-using loop that investigates and submits a ranked diagnosis with
  cited evidence.
- **Multi-agent (MA):** a Commander plans; metrics, logs and traces specialists investigate
  **concurrently** in separate contexts via `asyncio.TaskGroup`; deterministic checks and a Skeptic
  challenge the leading theory; the Commander adjudicates, may ask one targeted follow-up, and ranks.

Every claim either system makes must cite an observation that a validator checks, so neither can win
by inventing evidence. Two baselines with no LLM at all run on every case: one ranks services
straight from the anomaly digest (D1), the other is the benchmark's own BARO method (D0).

## Result 1: a tie at 3.4× the cost

Model: `gemini-3.1-flash-lite`. Ceiling: $0.33 and 24 model calls per incident, for both systems.

| | D0 (no model) | D1 (digest only) | Single agent | Multi-agent |
|---|---|---|---|---|
| AC@1 | 0.40 | 0.76 | **0.911** | **0.911** |
| Mean cost per incident | — | — | $0.0099 | $0.0340 |
| Mean wall time | — | — | 14 s | 18 s |

The pre-registered estimate of the difference is **0.0 points, 95% interval −8.9 to +8.9**. Both
systems got the same 39 incidents right and the same 2 wrong; the other 4 split 2–2.

The failure analysis suggested a tidy story: the single agent's distinctive errors were **reading
errors** inside one long context; the multi-agent system's distinctive errors were **coordination
errors** (a follow-up round overriding a correct answer). Two kinds of mistakes, cancelling out. The
follow-up experiments showed that story was only half right.

## Result 2: with a stronger model, coordination buys robustness

Re-running with `gemini-3.8-flash`, a thinking model, on the same 45 incidents:

| | Single agent | Multi-agent |
|---|---|---|
| AC@1 | 0.889 | **0.978** |
| Mean cost per incident | $0.080 | $0.113 (1.4×) |
| Difference | | **+8.9 points (95% CI +2.2 to +17.8)** |

The multi-agent system got 4 incidents right that the single agent missed. All four were runs where
**the single agent returned no answer at all**: throttled, timed out, or malformed output. On every
incident where the single agent produced a ranking, it was right. The honest summary:
**coordination bought robustness, not reasoning.**

## Follow-up experiments: four questions, four answers

A tie invites questions, so I ran four experiments — all pre-registered, all frozen before any run.

### A. Coordination or just more samples?

| | AC@1 | Cost per incident |
|---|---|---|
| Single agent, t=0 | 0.911 | $0.0099 |
| Multi-agent | 0.911 | $0.0340 |
| **Single agent, vote of 3** | **0.956** | **$0.0229** |

A vote of three beat the multi-agent system by 4.4 points at two-thirds of its spend. What fixed
the errors was running differently at all, not the voting mechanism.

### B. Is it memorizing these public demo apps?

Replacing every service name with an opaque code: **neither system lost accuracy**. A leak test
verified no original name reached any model.

### C. Does prompt wording matter more than architecture?

The gap between the two systems was **0.0 points under both wordings**. But the same rewording
changed the single agent's answer on **4 of 45** incidents vs **1 of 45** for the multi-agent
system. Coordination buys **stability**, even when it doesn't buy accuracy.

### D. Can either system tell when it is wrong?

| Signal | Accuracy on the most confident 70% | Errors caught |
|---|---|---|
| Self-reported "confident" | 90.6% | 1 of 4 |
| Multi-agent specialist agreement | 93.8% | 1 of 4 |
| **3 differently worded single-agent runs agree** | **100%** | **4 of 4** |

When three differently worded runs named the same service (89% of incidents), **it was right every
time**. The five disagreements contained all four errors.

## Phase 2: a simulated AI-infrastructure domain and a causal engine

Phase 1 showed that a well-built single agent is surprisingly hard to beat. But on real incidents,
the agent investigates freely — there is no notion of "this test could have told me something that
test could not". Phase 2 asked: **what if the agent reasons causally?**

I built two things:

**SIM-AI** is a simulated AI-infrastructure incident domain: an LLM chat platform with a gateway,
two inference replicas, a RAG retrieval path, a vector database, and a Kafka indexing pipeline — 10
services, 10 fault classes with look-alikes, and a 16-class taxonomy where 6 classes are decoys the
simulator never produces. The simulator uses a fluid model that propagates faults causally through
the call graph, so temporal signals (which service moved first) carry real diagnostic information.

**The Causal Engine (CE)** is a third arm that replaces free tool use with a structured investigation
loop:

<CausalEngine />

1. **Form hypotheses** from the anomaly digest, each with a Bayesian prior proportional to its anomaly
   score, plus an `other` bucket (prior 0.15) excluded from information-gain calculations.
2. **Design discriminating tests** — candidate tool calls scored by expected information gain over the
   stated hypotheses, with a 0.05-bit threshold to prevent useless tests.
3. **Predict outcomes before running the tool** — predictions are journaled before execution, making
   the "predict, then observe" claim auditable.
4. **Update beliefs** — Bayesian posterior update on observed predicates. Stop when top belief ≥ 0.80,
   at least one test has run, and the leading hypothesis has accepted supporting evidence.

### Where the causal engine wins: retry-storm

Retry-storm faults create a cascade: the gateway overloads, callers retry, and the blast radius
grows until the anomaly digest points at the wrong service. The single agent follows the digest's
misleading top anomaly and blames the caller every time.

| | B1 | MA | CE |
|---|---|---|---|
| Retry-storm accuracy | **0.06** | 0.56 | **0.72** |

The causal engine scores **12× higher** than the single agent on retry-storm faults. Its
predict-then-test loop asks "which service moved first?" and "did the caller's load increase before
or after the gateway's errors began?" — causal questions that free tool use never thinks to ask.

### Where the causal engine knows what it doesn't know

The best finding: CE's confidence signal actually works. Across all 60 holdout incidents:

- When CE answered at belief ≥ 0.80: **88.5% accuracy**
- When CE answered below 0.80: 66.4% accuracy

The x1 experiments on Phase 1 had already shown that self-reported confidence ("I am confident this
is the root cause") was useless — the single agent said it every time. The causal engine's belief
score, grounded in the observed outcomes of tests it designed and predicted, gives an **honest
calibration signal** that could actually gate escalation to a human.

## A benchmark that cannot cheat

I built both the simulator and the engine, so the benchmark could easily be self-fulfilling. Seven
controls prevent it:

1. **Gate G-sim:** the zero-inference baseline must land in a band (0.35–0.75) on dev, so the
   benchmark is neither trivial nor impossible. It passed on the first try (D1 = 0.72).
2. **Mechanism unit tests** for every fault (causal order of signals), independent of the agent.
3. **Import-linter** keeps `ic.sim` out of the decision path — the agent code cannot import
   simulator internals.
4. **Six decoy fault classes** the simulator never produces, sorted alphabetically with real classes
   so schema order does not leak which are real.
5. **Prompt lint** ensures prompts can explain signals but never say "pattern X means fault Y".
6. **Pilot difficulty control:** B1 must stay below 0.90 on dev. When it hit 0.93 after a fairness
   fix, one arm-neutral adjustment (lower fault severity) brought it back.
7. **The freeze covers the generator**, not only the agents. A one-line simulator change after the
   freeze makes the holdout gate refuse to run.

## Phase 3: benchmarking against an open-source SRE agent

The first two phases compared systems I built against each other. That is useful for understanding
tradeoffs, but it leaves a question: **how do they compare with something someone else built?**

[HolmesGPT](https://github.com/robusta-dev/holmesgpt) is the most widely deployed open-source SRE
agent — an Apache-2.0 CNCF project with its own investigation loop, tool management, and system
prompt. I ran it **unmodified** (pinned at commit `7745255`) on the same 45 RE2 incidents, under
the same protocol as my agents:

- **Same model** for every arm: Claude Haiku 5.5
- **Same tools**: the seven read-only telemetry tools, served over MCP
- **Same limits**: $0.10, 24 model calls, and 600 seconds per incident
- **Same scorer**: identical submission and evaluation pipeline

Two variants: `holmes` (plain, with the task description but no investigation advice) and
`holmes-guided` (with B1's two domain-advice bullets, verbatim).

HolmesGPT beat the single agent by **+8.9 points (95% interval +0.0 to +20.0)** and matched the
multi-agent system at 42% of its cost. It ran cleanly on all 90 runs, with no forced submit and
no crash. It was cheaper because it batches tool calls — about three per model turn, resending its
context a third fewer times than B1.

On Claude Haiku (unlike the Phase 1 tie on Gemini Flash-Lite), coordination helped: **MA led B1 by
11.1 points (+0.0 to +22.2)**. The multi-agent advantage depends on the model.

### The finding that changed my assumptions

B1's prompt includes two bullets of domain advice: *"a slow caller is often a symptom"* and
*"follow calls downstream."* On 3 of its 5 misses, B1 followed this advice and blamed a downstream
service instead of the true root: a delay in `recommendationservice` attributed to
`productcatalogservice`, a delay in `checkoutservice` attributed to `shippingservice`.

When I gave HolmesGPT the same two bullets, **it reproduced B1's exact wrong answers** on 3 of 5
cases — including the `recommendationservice` miss. Two sentences of domain advice, transplanted
into a completely different runtime with a different system prompt, investigation loop, and tool
management, and the same systematic error appeared.

**Domain heuristics that feel right can create systematic blind spots, and they transfer across
runtimes.** This is the kind of result that changes how you design agent prompts: advice that is
correct "most of the time" can be worse than no advice at all, because it creates a consistent
failure mode instead of random errors that averaging can fix.

### Integration engineering

The largest dev-phase effect was not a model or prompt issue — it was a **schema-flattening bug in
HolmesGPT's MCP integration**. HolmesGPT rebuilds tool schemas and strips nested `enum` and
`description` fields, so its model saw `claims[].direction` as a free string instead of
`for`/`against`. Every one of 26 dev runs needed its one allowed repair on `submit_diagnosis`. The
fix: serve the project's own specs directly, bypassing HolmesGPT's schema processing. On the
holdout, 8 of 90 runs used their repair — down from 100%.

## What this means for teams building agent systems

1. **Benchmark against an external system, not just your own.** HolmesGPT, unmodified and
   untuned, beat my single agent and matched my multi-agent system at a fraction of the cost. If
   you only test your systems against each other, you may be optimizing in a local minimum.
2. **Domain advice can be worse than no advice.** Two sentences of investigation heuristics created
   the same systematic errors in two completely different runtimes. Advice that is right "most of
   the time" creates a consistent failure mode that averaging cannot fix.
3. **Perturb and vote a single agent before building a multi-agent system.** Three differently worded
   runs of one agent matched or beat the multi-agent system's accuracy at the same or lower spend.
4. **Know what coordination actually buys.** Here it was not better reasoning. It was stability
   across prompt versions and robustness to timeouts on a slow model — and the effect was
   model-dependent (appeared on Claude Haiku, not on Gemini Flash-Lite).
5. **A structured investigation loop beats free tool use on hard, confounded cases.** When the
   symptom and the cause are separated by several hops, predict-then-test finds what open-ended
   investigation misses.
6. **Get the abstention signal from disagreement or Bayesian belief, not from the model's words.**
   Self-reported confidence was useless; the causal engine's posterior and cross-run agreement both
   caught real errors.
7. **Coordination has its own failure modes; write its rules as code.** A follow-up that re-asks the
   dissenting specialist is not independent evidence. On dev it turned six right answers wrong.
8. **Fair comparison is mostly interface work.** The largest dev-phase effect was a schema-flattening
   bug in the integration, not in any model or prompt: 100% of dev runs needed a repair before the
   fix; 9% after.
9. **Build the benchmark controls before the benchmark.** The decoy classes, the gate, the import
   fence and the prompt lint exist to make the results credible, not to make them better.

## How the study was run

The comparison is only worth anything if it is fair and reproducible, so most of the engineering went
there:

- **No peeking.** A grouped dev/holdout split committed before any run; holdout labels reachable
  through one package only, enforced by an import-linter rule; for each experiment, a
  pre-registered analysis plan and a freeze file hashing the model, budget, prompts and every file
  on the decision path; a holdout runner that refuses to start if any hash differs.
- **Sandboxed external agent.** HolmesGPT ran as its own process from a pinned venv, in a
  temporary directory with its own `HOME`, no inherited environment and no credentials. It reached
  only a loopback server serving an OpenAI-compatible endpoint (every call budgeted, ledgered and
  journaled) and the MCP tools. Each request was checked against a tool allowlist: its shell,
  internet and Kubernetes toolsets were switched off so it could not see anything B1 could not.
- **Equal information.** Both systems get the same alert time through one shared header function,
  byte-identical across arms (`test_case_header_parity.py`).
- **Money safety.** A fail-closed model registry, worst-case cost reservations, a ledger,
  per-incident caps, and phase stops enforced in code. Each paid phase ran under a hard cap set by
  the owner.
- **Reliability.** `asyncio.TaskGroup` fan-out where no worker failure can cancel its siblings;
  retries with backoff; six injected-fault scenarios (rate limit, timeout, malformed output, crash,
  invalid evidence, killed runner) tested in CI with a scripted model at $0.
- **Observability.** Every run's journal converts to OpenTelemetry traces (agent, LLM and tool spans
  with token counts and cost) viewed in a local Arize Phoenix. A static HTML replay per run shows
  the parallel agents, the hypothesis board and every claim linked to its evidence.
- **Reproducibility.** Real runs record to cassettes and replay byte-for-byte; every analysis
  regenerates in one command; a clean-clone check rebuilds and tests the repository from scratch.
- **Provider outage handling.** 42 of 540 holdout units failed with "unavailable". Because the
  pre-registration specified which failures get one rerun (status and error kind only, never a
  score), the reruns took ten minutes and no judgment.

Things that went wrong, and were caught before they could bias a result:

- **Budget estimates, not dollars, were binding.** A guard sized calls on pessimistic token
  *estimates*, which starved the multi-agent system.
- **One dissenter could overturn a majority.** A coordinator rule allowed it, until a two-specialist
  rule replaced it.
- **The stronger model rejected our message format.** It refused text placed after a tool result,
  which broke the coordinator on every call.
- **Time limits were sized for the fast model.** The slow model's latency spikes turned into
  failures.
- **The model was right; the simulator was wrong.** CE's first dev run failed 15 of 40 cases. Every
  miss had the true cause among its first hypotheses. Tallying which predictions failed pointed at
  `onset_order`: 40% of results were "tie" and half the lags were exactly 0 s. The fluid simulator
  had no notion of propagation delay between services. Treating a tie as "can't tell" lifted CE
  from 0.57 to 0.72. The simulator stays as is and its zero propagation delay is reported as a
  limit.
- **Asking for the answer you score.** The glossary told agents to name a fault class only when
  sure. That was harmless under the old metric, and a 5-of-10 error source under joint accuracy.
  Changing one sentence for every arm moved B1 from 0.75 to 0.93.
- **A reporting bug hid HolmesGPT's cost.** The first generated report showed $0 for both
  HolmesGPT arms; the journal reader looked for their charge on the wrong event. The reader was
  fixed and the report regenerated — accuracy unchanged, cost rows corrected.

## What I built, and how

I designed the study, the systems, the simulator, the evaluation protocol, and made every decision
about models, budgets, fairness and what counted as a result. Implementation was done by AI coding
agents (Claude Code and Codex) working from written work-package briefs, each in its own git
worktree, merging only through pull requests with green CI, under rules I set: no agent could touch
the data contracts, read holdout labels or spend money. Later, I delegated the paid runs and holdout
steps to the orchestrating agent within hard spend limits enforced in code, with every delegated
decision labelled as such.

**What this demonstrates**, for anyone hiring for senior or staff AI engineering:

- **Designing and running a pre-registered evaluation** of agent architectures across two domains
  and an external baseline, reporting a null result, a surprising positive result, a negative
  result, and the follow-ups that explained each — correcting my own earlier claims when the
  evidence changed.
- **Benchmarking against external systems** (HolmesGPT, a CNCF open-source agent), including
  integration engineering (finding and fixing a schema-flattening bug in the MCP layer) and
  reporting a result where the external system outperformed my own.
- **Discovering transferable insights about agent design**: domain advice that creates systematic
  errors regardless of the runtime it is embedded in — a finding with implications for any team
  writing agent prompts.
- **Building a novel agent architecture** (the causal engine) that outperforms established
  approaches on specific, measurable strata, with an honest calibration signal.
- **Building production-shaped agent systems**: concurrency with `asyncio.TaskGroup`, budget guards,
  failure handling with six tested fault scenarios, evidence validation, deterministic replay,
  observability with OpenTelemetry and Phoenix.
- **Designing a simulated benchmark with controls against self-fulfilling results**: import fences,

- **Cost-aware engineering**: every call priced, capped and accounted for; eight experiments across
  two domains for $51.
- **Directing AI coding agents at scale** (~200 PRs) with guardrails, review checkpoints and an
  auditable decision trail.
